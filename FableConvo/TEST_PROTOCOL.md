# TEST PROTOCOL — the ledger-first loop

**Adopted 2 July 2026.** Design goals: forward momentum, minimal red tape, zero
unauditable claims. Rule of thumb: if the paperwork for one test exceeds ten lines
before the run and ten after, the template is wrong, not you.

## Scope — what binds and what does not

- EXPLORATION IS FREE. Walking the geometry, musings, probing sessions, viewers,
  conjectures: no ledger required. File outputs to the musings tier as you go.
- THE PROTOCOL BINDS the moment a claim wants a STATUS. No number may appear in
  CLAIMS_STATUS, a README headline, or a public post unless it went through the loop.

## The loop (five steps)

STEP -1 - TRANSLATION FIDELITY (when a Dylan musing or ontology is being
operationalised). Apply `ARA_TRANSLATION_FIDELITY_PROTOCOL.md`. Freeze the
verbatim source, mathematical object, back-translation, forbidden proxies and
Dylan's explicit fidelity verdict. No `EXACT ENOUGH TO TEST`, no ARA test.
Previously run wrong-object instruments are retained as `PROXY TEST`, not
negative ARA evidence.

**Compaction override (30 Jul 2026):** if context compacts between proposal
and execution, the earlier sign-off no longer authorises a run. Retrieve the
durable record, restate identity, axis/relation, ordered poles, observable and
forbidden neighboring proxy, then ask Dylan again for `EXACT ENOUGH TO TEST`.
Do not freeze or run until he reconfirms. A post-compaction test run without
that reconfirmation is automatically a construct-invalid proxy test.

STEP 0 - REGISTER FIRST (before any code runs on real data).
Add an entry to MASTER_PREDICTION_LEDGER.md:

    ### T<number> - <short name>
    REGISTERED: <date> | STATUS: REGISTERED
    Orientation: <up=slower/larger unless stated>
    Claim: <one sentence>
    Test: <what will be measured, on what data, with what method/script planned>
    Prediction: <the number/direction/shape expected>
    Falsifier: <what result kills it>
    Rivals: <competing constants/models that must be reported alongside>

STEP 1 - RUN. Strict-causal rules per CANON section 3. Canonical mapper for duties
and bands. Calibrate extractors first if the measure lives in a crowded neighborhood.

STEP 2 - RECORD (same ledger entry, appended):

    Script: <path> @ git commit <hash>
    Data: <source + URL + download date> | Ran: <date>
    Raw result: <the numbers, uninterpreted, incl. CI if n is small>
    Artifacts: <result .json/.png paths - committed, never left in /tmp>

STEP 3 - INTERPRET AND RATE (Dylan's words, then the rating):

    Interpretation (Dylan): <what you think it means, plainly>
    RATING: <from the scale below>

STEP 4 - PROPAGATE. If the rating changes a claim's tier: update CLAIMS_STATUS.md.
If it kills something: add to SUPERSEDED.md and mark the old doc, do not delete it.
Summary totals: regenerated by script only, never hand-edited.

## The rating scale (fixed vocabulary - use no other words)

- CONFIRMED   - pre-registered prediction, survived controls AND independent
                replication (different machine/person/code).
- SUPPORTED   - positive result, controls passed, not yet replicated or underpowered.
- SUGGESTIVE  - direction matches, fences large (n small, one system, proxy measure).
- INCONCLUSIVE- measurement-limited: the instrument could not decide (bias > gaps,
                degenerate floors, failed splits). NOT evidence either way.
- NULL        - instrument adequate, nothing found. An honest null is a result.
- NOT SUPPORTED - the prediction failed cleanly. Also a result.
- RETRACTED   - previously claimed, later killed. Keep the corpse visible.
- PARKED      - musing tier: conjecture with anchors, no test specified yet.
- RULE        - methodology law adopted into CANON.

Modifiers worth appending in brackets: [pre-registered] [replicated xN] [n=?]
[generic extractor] [canonical].

## Hygiene checklist (solidifying what you already do)

1. Data provenance: source, URL, and download date in every script header.
2. Determinism: fix seeds; scripts print their own provenance table.
3. No orphan results: every RESULT.md names a committed script that reproduces it
   (the /tmp graveyard from the June audit must not regrow).
4. Per-origin causal baselines in anything walk-forward (anomalies/detrending
   recomputed from past data only).
5. Competing constants and the crowded-neighborhood rule, always (CANON section 3).
6. Calibrate every extractor against synthetics at the record's own SNR and length.
7. Split-half stability check on every surprising win; block bootstrap on small n.
8. Negative control for every new instrument (run it on designed randomness).
9. Orientation signature line at the top of every new document.
10. Provenance tags in visualizations: every plotted coordinate is MEASURED or
    ASSIGNED, and the viewer says which. Derived axes (phi-lines etc.) carry their
    derivation or the label "aesthetic fixture."
11. Session archiving: at session end, copy the whole local_<id> folder into
    transcripts/local_sessions/. The transcript is archive-only (contains gated
    vocabulary) - point future AIs at excerpts, never paste it whole.
12. Gated-vocabulary quarantine: fusion/battery-nuclear and organics application
    docs live in their own folder with a stub reference, so the core repo stays
    discussable with any AI.
13. New AI session ritual: load CANON_FOR_AI.md first; the AI restates the three
    laws most relevant to the task before touching data.
14. Weekly (or per-session): regenerate summary tables by script.
15. Monthly-ish: one adversarial audit pass (self or AI) on the newest claims;
    audits are commissioned against your BEST results, not your weakest.
16. Two-output reporting: never let a benchmark/status verdict replace the ARA
    geometry disclosure. Record both even when one is NULL or NOT SUPPORTED.

## RULE - two-output ARA reporting (added 20 Jul 2026)

Every ARA test report must state two conclusions separately:

1. **Claim or benchmark verdict.** Did the registered prediction beat its
   control, pass its falsifier and satisfy the frozen status criteria?
2. **Geometry verdict.** What actually appeared on the ARA coordinates,
   including structure shared by the target and controls?

The geometry verdict must expose, when the data permit:

- the raw 0-2 coordinate definition and orientation;
- population distributions, quantiles, range and sample count - not only means;
- individual event examples as well as the population aggregation;
- lead / at-event / lag traces around predeclared or post-hoc key events;
- crests, troughs, ridges, crossings, flips, singularity-well occupancy and
  relevant Phi-handover regions;
- parent, current-rung and child readings without flattening them into one score;
- the same geometry for controls or rival populations;
- negative, absent and shared geometry;
- an explicit label separating frozen confirmatory results from post-hoc
  descriptive discoveries.

A NULL predictive result does not mean "no geometry." A rich descriptive shape
does not rescue a NULL prediction. Both statements can be true and must remain
visible together. The short ledger entry may summarize them, but it must link to
the full geometry table/CSV and at least one worked event when those artifacts
exist.

**Reporting failure condition:** a report is incomplete if it gives only the
status/benchmark headline while omitting event-centred geometry already computed
or available from the same run. Compression is acceptable only after the full
record exists and is linked.

## Momentum rules (anti-red-tape, learned the hard way)

- Close before you open: one live REGISTERED test per thread; consolidation beats
  breadth (twenty thread-folders in two months was the failure mode).
- The bath-share meter decides where prediction effort goes: if the residual floor
  is high, the missing rules mostly are not there to find - spend elsewhere.
- Wrong-in-a-specific-way beats right-in-a-vague-way: register predictions sharp
  enough that their failure teaches something (the 27-month ring mismatch found the
  second band; the detector upgrade shrank an effect and strengthened the claim).
- The musings folder is sacred ground for momentum: no protocol there, ever. The
  protocol exists so the musings can stay free.

## RULE — out-of-the-box replication (added 3 Jul 2026)

Every committed test script must run from a fresh git clone with zero manual
setup. Concretely:

1. **Data auto-fetch.** The script may rely on data being at a relative path
   inside the repo; if the file is absent, the script DOWNLOADS it from the
   canonical public source before running. The download URL, DOI, and a
   checksum (or expected row count) live in the script header next to the
   pre-registration — provenance and prediction travel together.
2. **Synthetic/ground-truth scripts** (calibrations, digital rigs like
   `digital_rig_L1.py`) must be fully self-contained: fixed seeds, no inputs.
3. **Gated or local-only data** are the one exception: ship a small included
   sample so the script still executes end-to-end, plus a header note stating
   what the authoritative dataset is and how to obtain it. The script must
   never crash on a fresh clone — worst case it runs the sample and says so.
4. **Config stays at the top** of the file (paths, sample rate, seed), and
   defaults must be the replication defaults — a stranger typing
   `python script.py` gets the registered result, digit-identical.

Why: replication is the product. A result that needs the author present to
reproduce is testimony, not evidence.

**First retrofits (3 Jul, tested end-to-end in sandbox):** `test6_dissociation.py`
and `test6b_driven.py` now auto-fetch Zenodo 10.5281/zenodo.6633719
(MultiArm-Pendulum.zip, md5-verified) into `pendulum_data/` beside the script.
Verified: fresh empty dir -> download -> md5 pass -> extracted files
byte-identical to the copies the registered results were computed from ->
second run is a no-op. One portability bug caught and fixed in testing: the
archive must live beside the data (DATA_DIR), never in a system temp dir —
temp paths differ across machines and can silently double-download.

## RULE — synthetic data (lineage: THE_FRAMEWORK_FORMULATION.md §10, burns in
## scripts 02 and 109/110)

Real, sourced public data for headline results; synthetic for method
demonstration ONLY. The discriminating question: is the synthetic structure a
KNOWN REFEREE (exact equations used to validate instruments — legitimate;
e.g. circle map, identified-pendulum ground truth) or a possible UNKNOWN ECHO
(generated/estimated values whose assumptions the analysis then "discovers" —
poison; the script-02 powers-of-10 burn, the script-109 circular band)?
Synthetic conclusions are permitted about INSTRUMENTS, never about the world.
Calibrate on synthetics at matched noise; adjudicate on real data.
